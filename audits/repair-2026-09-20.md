## The two that were claims about evidence, not code

**L01 — the 310 and 301 "ungradable" volatility forecasts are a warm-up
boundary, not a fault.** Measured on the live database: 310 of 310 at h=1 and
301 of 301 at h=5 are that symbol's earliest forecast, and no symbol has more
than one. They all carry the same reason, "the outcome window never became
fully estimable". A symbol's first forecast is made before there is enough
forward data to estimate its outcome window; the second one is fine. This is
5.4% and 5.3% of each horizon and it does not grow.

**L02 — the accounting is sound, and my first reading of it was wrong.** I
initially read `resolved_ts IS NOT NULL` as "graded" and found 310 rows that
looked doubly counted. `MarkRVUngradable` sets `resolved_ts` as a CLOSE time
while leaving `actual` NULL, and the API counts `actual IS NOT NULL AND actual
> 0`. On those columns the overlap is exactly 0, and the counts reproduce the
page: 5,104 graded / 310 ungradable / 10 distinct call-days at h=1, and 3,978 /
301 / 6 at h=5. No defect.

**L03 — I could not measure the monitor's coverage ratio and am not reporting
one.** What I can say: the latest snapshot day, 2026-09-20, is a **Sunday**;
`model_forecasts` carries 1,684 rows over 331 symbols that day while `forecasts`
carries none, which is consistent with a closed market and not with an
ingestion outage. On the most recent full trading day, Friday 2026-09-18,
admission is plainly working: 303 symbols received a forecast. I then tried to
compute coverage as a ratio between those two tables and got impossible values
(>1 on several days), because they are written on different cadences and their
`ts` columns do not mean the same thing. That ratio is not the one
`forecastmon.RawDayStats` computes, so I discarded it rather than publish a
number I could not defend. **Running the monitor's own code path over a session
calendar is the correct measurement and I did not do it.** Until someone does,
"no model qualifies" remains the honest reading and the admission gate has not
been shown to be broken.

**L04 — `tools/deployment_drift.py` is RED, and it should be.** It reports the
running daemon at `3f77e42` with one later commit touching `daemon/`. That
commit is `a34d6a8`, from this pass. The repository's own rule applies: a red
drift check means DEPLOY, never backfill. It clears when the daemon is rebuilt
and restarted; deploying is out of scope for this pass and is the owner's call.

## What each fix actually changed

**F01.** The gate asked whether a key existed, never what was under it.
`{"generated":"not-a-date","rows":[null]}` PASSed with zero rows checked; an
honesty block with the right source and all four required keys set to `null`
PASSed with checked=1; and `NaN` — which `json.load` accepts by default — PASSed
too, as does `1e400`, which overflows to `inf` with no literal at all (N01, not
in the audit). It now validates shape and only shape: the timestamp must parse,
every row must be an object, and an honesty block must carry booleans where
`verdict()` returns booleans, a string reason, and the typed record
`skillschema.build()` stamps. It still reads no verdict and compares no number
against a threshold — a REFUSED row passes, a NO_INTERVAL row passes, and a
refusal with an *empty* reason does not, because that is a truncated write.

The suite's own `HONESTY_OK` fixture was `{"result": {"schema": "skill/1"}}`, a
shape no version of `selection_honesty.py` has ever written (N03). It only
survived because the old gate never looked inside.

**F02.** Freshness is measured once, before any branch, and reported on every
path. A new `grader_stale_reason` carries the heartbeat's sentence so a refused
window that *also* has a stale heartbeat discloses both. Branch order is
unchanged and no refusal publishes a row.

**F09.** Four levels are now reported apart — stored-head comparison, payload
recomputation, valid local signature, external witness — and the field that
names the operator is gated on the last, which nothing can currently satisfy.
`ledger_anchors` stores no witness reference, and `meta.anchor_last_published`
is a timestamp this machine wrote about its own publish script: a claim to
check, not a receipt, and writable by anyone who can rewrite the ledger. The
`provenAnterior*` numbers keep their values and gain `anteriorityScope`, which
states in the payload that they constrain an adversary *without* the key.

**F10 / R02.** `${OUT}.staging` was one fixed name with no lock. A single-writer
`mkdir` lock plus a per-run staging file fixes the race; a declining run writes
no heartbeat and no envelope, because the holder is about to write both. A
measured collapse now records `--refused` (a healthy grader that declined) and
only genuine outages record `--failure`, matching the dev-box classification
character for character. The container also writes the same structured refusal
envelope the dev box does — previously it left `$OUT` untouched, so a seeded
volume kept serving stale rows silently and a fresh volume had no file at all,
which reads as an outage rather than a refusal.

N02: a process killed between `mkdir` and writing its pid left a lock nobody
owned and nothing could break — every later run would decline forever, which
looks exactly like a dead grader. Age alone breaks a pid-less lock now.

**R03.** The manifest bound 6 source files. It now binds 11, including
`skillpower.py` and `skillschema.py` — imported by `selection_honesty`, so their
bytes decide a verdict — and `ops/grade.sh` and the entrypoint, verified at the
path they RUN from rather than their repository path. The docstring states the
boundary, including what it does **not** cover: an operator who can replace the
image can replace the manifest and this verifier with it, and no self-contained
check survives that. The value is against drift and against a swap inside a
running container.

## Environment blockers, kept separate from product failures

**A real container run was not possible on this host.** `docker info` reports
`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`
— Docker Desktop is not running, and starting it is an environment change this
pass did not make on its own initiative. So the F10/R02 "fresh volume" and
"seeded volume" cases are exercised at the WRAPPER level, in throwaway sandboxes
with their own `$OUT`, `$DB`, `$TOOLS` and PATH, driven through the same
`SIGNALDECK_*` variables the container sets. That is a real execution of
`ops/grade.sh` under a real POSIX shell, and it is **not** the same thing as a
run inside the image. The remaining container-specific risks — busybox `sh`
versus Git's `sh.exe`, the entrypoint's schedule, `/data` volume permissions —
are untested here and named so nobody reads a green wrapper suite as a green
container.

**One lock test skips on this host** because `kill -0` cannot see a Win32 pid
from MSYS `sh`. In the container the holder and the wrapper share a PID
namespace, where `kill -0` is exactly the right probe. The skip prints that
reason; it is not silent, and the stale-lock half of the pair does run.

Not done: container end-to-end on a real Docker volume, load test, restore
drill, full authenticated UI sweep, full ledger walk (`?full=1` on 533k rows),
licensing review, and the forecast-monitor coverage measurement in L03.
